# 量化系统审计修复

## 角色结构

- 主线程是唯一 A Controller。
- B、C、D 可用于调查；B、C 永远只读。
- D 只允许修改批准的测试文件；E 只允许修改批准的生产文件。
- `a_controller` 仅在用户要求第二总控复核时启动，正常流程不嵌套启动 A。

## 标准门禁

### Gate 0：现场安全

先核验项目根目录、分支、HEAD、工作区、stash、Python、数据文件和导入路径。工作区不干净时先保护用户修改，不能删除或覆盖。

### Gate 1：问题分类

A 将问题分类为生产缺陷、测试覆盖不足、测试基础设施、设计观察项或当前无需修改，并冻结问题编号、业务契约、允许文件、禁止范围和验收条件。

### Gate 2：独立调查

A 可并行启动 B（架构和真实调用链）、C（业务契约）和 D（测试与最小复现调查），等待三者全部返回。读任务可并行，写任务不得并行。

### Gate 3：红测试

确认生产缺陷后，A 批准 D 的范围。D 在独立分支或隔离 worktree 建立红测试并创建测试 commit。A 必须核验 parent、文件范围、旧代码稳定失败、控制测试通过及失败并非夹具错误。未通过不得进入生产修复。

### Gate 4：最小修复

E 从获批测试 commit 开始，只修改批准的生产文件，不修改测试。每个问题使用独立生产 commit，并运行专项、相关回归、语法检查和必要反事实验证。

### Gate 5：第一层验收

A 检查 commit parent、修改文件、精确 diff、专项结果、parent/candidate 节点集合和环境一致性。candidate-only failure 不为零时立即停止。

### Gate 6：最终独立验收

修复后重新启动 B、C、D，分别执行架构终审、业务契约终审、测试顺序变形和反向破坏终审；旧报告全部失效，必须基于最新候选重新执行。

### Gate 7：关闭

只有主线程 A 可以关闭问题。必须满足 B 无阻塞、C 无阻塞、D 反向破坏可重现缺陷、parent/candidate 同环境对照无 candidate-only failure、工作区干净，并且用户明确允许合并和推送。

## Git 规则

- 每个问题使用独立分支；测试 commit 与生产 commit 分离。
- 只读审查可以并行，D 和 E 写入严格串行。
- 禁止 amend 已验收 commit，禁止自动删除 stash。
- 未经用户明确允许不得 push、merge 或删除分支/stash。
- 出现冲突、范围扩大或环境不一致时停止，不猜测。

## 固定输出

每轮报告当前问题、Gate、分支和 HEAD、已启动 Agent、各 Agent 状态、根因、测试/生产 commit、专项结果、parent/candidate 对照、阻塞事项、下一步及是否需要用户批准。

## 已关闭事项保护

除非有独立新证据并建立新问题编号，不得重新修改 BUG-P2-006、BUG-P1-005A、BUG-P1-005B、市场流动性观察 UI 或默认严格预挂单配置契约。
